# fingerprint-browser 产品级缺口审计

> 版本：v0.2.0-rc1 ｜ 审计日期：2026-08-29 ｜ **只读审计**（本轮未修改任何源码、未启动任何 benchmark）
> 配套：`PRODUCT_ARCHITECTURE.md` · `PRODUCT_CAPABILITY_MATRIX.md`

---

## 摘要：五个最重要的判断

1. **这不是一个产品，这是两个成熟度差 2–3 个量级的东西挤在一个仓库里。**
   「指纹浏览器」可用但缺商业化外壳；「AI Browser Operator」架构罕见但业务成功率 **6/100**。当前所有注意力（35 份 `PHASE*.md`）都在后者身上，而能交付的是前者。

2. **最严重的问题不在功能，在工程与安全。**
   系统托管大量账号密码与信用卡号，却**零鉴权 + CORS 全开 + 绑定 0.0.0.0**；同时**没有 `.git`、没有 CI、没有 LICENSE、没有 `npm test`**。这些不是「好不好用」，是「能不能交付」。

3. **AI 功能的瓶颈不在算法，在「最后一公里接线」。**
   6 个动作（`upload`/`download`/`openTab`/`closeTab`/`switchTab`/`dialog`）**在 `tools.js` 已实现、浏览器层也具备能力，却被 `schema/action.js` 的 `ACTION_TYPES` 拦死，永远执行不到**；`HUMAN_ESCALATION` 是终态，升级即死亡。修复成本远低于任何架构重构。

4. **团队协作为零，这是与商业产品之间最宽的鸿沟。**
   所有主流产品（AdsPower / 比特 / Multilogin / Kameleo）都以用户体系、角色权限、操作审计、按席位收费为核心商业模式。本项目在这四项上**全部为 0**。

5. **代理与网络是本项目真正强于竞品的模块，**应作为差异化卖点而非被忽视的角落。
   自研 SOCKS5 认证 shim（绕开 Chromium 原生限制）+ 代理→时区/语言/地理自动对齐 + 失败即阻断绝不回退直连，这套组合在同类产品中是优等生。

## 审计方法与局限（必须先声明）

| 项 | 说明 |
|---|---|

## 一、能力缺口（CAP）

> 定义：产品「该有而没有」的功能性能力，直接影响用户能否完成工作。

| ID | 缺口 | 证据 | 影响 | 修复成本 | 优先级 |
|---|---|---|---|---|---|
| **CAP-01** | **零用户体系 / 零鉴权 / 零权限分级** | 前端 grep `token\|Bearer\|localStorage` 零命中；`server/` 无鉴权中间件 | **任何团队客户不可用**；无法按席位收费；无法追责 | 大（2–3 周） | **P0** |
| **CAP-02** | **无批量操作**（批量创建 / 批量改指纹 / 批量绑代理 / 批量导入导出） | 无 batch 接口 | 运营团队开 50 个店铺要手工点 50 次；**刚需** | 中（1 周） | **P0** |
| **CAP-03** | **Profile 导入导出缺失**（仅 Cookie，且需浏览器运行中） | `index.js:484-495` | 无法迁移、备份、交接；企业客户必问 | 中（3–5 天） | **P0** |
| **CAP-04** | **浏览器查看器不能操作**（只能看截图 + 手动导航） | `BrowserViewer.jsx` 未调用后端已实现的 `human-click`/`human-type`/`human-move`/`human-scroll`（`index.js:312-347`） | **用户必须去本机真实窗口操作**，产品体验断裂 | 中（1 周，后端已有能力） | **P0** |
| **CAP-05** | **6 个已实现的 AI 动作被 schema 拦死** | `ACTION_TYPES`（`schema/action.js:9-14`）不含 `openTab`/`closeTab`/`switchTab`/`upload`/`download`/`dialog`，而 `tools.js:411,418,427,519,532,562` 已实现 | 真实业务流程（导出报表要处理下载弹窗、多标签页比价）**直接不可用** | **小（1 天，纯接线）** | **P0** |
| **CAP-06** | **`HUMAN_ESCALATION` 是终态，无出边、不能重试、无接管界面** | `taskStateManager.js:14`（在 `TASK_TERMINAL` 中）；`taskManager.retry` 只接受 `FAILED/CANCELLED`；`TaskDetail.jsx:156` 仅渲染一行文本 | **AI 升级人工 = 任务死亡**，89% 的任务止步于此 | 中（3–5 天） | **P0** |

| **CAP-08** | **指纹注入痕迹可被直接枚举** | `__fpGID = true` 普通赋值（`inject.js:310`）；`whiten()` 返回无名函数；伪造 `window.chrome.runtime`（真实环境应为 `undefined`）；`deviceId` 每次随机 | 一个 `Object.getOwnPropertyNames` 就能识别 → **反检测产品在检测面前裸奔** | 小–中（3–5 天） | **P1** |
| **CAP-09** | **无可视化 RPA 流程编辑器 / 无录制回放** | `selfHealing/` 为空目录（0 文件） | 这是 AdsPower 的核心护城河；非技术用户无法自助自动化 | 大（4–8 周） | **P1** |
| **CAP-10** | **无 Selenium / Puppeteer / Playwright 接入**，仅有 `/browser/:id/evaluate` 执行任意 JS | `index.js:297` | **开发者生态入场券缺失**；所有主流产品均支持 | 中（1–2 周） | **P1** |
| **CAP-11** | 时区 JS 层未覆盖 `getTimezoneOffset`，且 `fp/data.js` 注释与实现自相矛盾 | `inject.js:233-241`；`data.js:39` vs `:50` | 地域一致性是防关联核心项，JS 读穿即暴露真实时区 | 小（1 天） | **P1** |

| **CAP-16** | IP 信誉预检仅告警不改行为 | `proxyPrecheck.js` | 用户可用机房 IP 开广告账户 → 高封号风险，产品无法保护用户 | 小（策略开关） | **P2** |

## 二、场景缺口（SCN）

> 定义：能力「有」，但拼不成一条完整的用户旅程，导致用户在实际工作流中卡住。

| ID | 场景 | 断点在哪 | 后果 | 优先级 |
|---|---|---|---|---|
| **SCN-01** | **团队协作运营**（多人共管 100 个店铺环境） | 无用户体系、无角色、无审计、无环境共享 | **整条场景不存在** | **P0** |
| **SCN-02** | **新人接手同事的环境** | 无 Profile 导出、Cookie 导入需运行中、前端导入框输入被静默丢弃（`ProfileEditor.jsx:330` vs `:816-849`） | 交接只能靠「把电脑交给他」 | **P0** |
| **SCN-03** | **批量开店**（一次创建 50 个环境并分别绑代理） | 无批量接口，只能逐个手工创建 | 人力成本 O(n)，运营团队直接劝退 | **P0** |
| **SCN-04** | **AI 导出报表**（点导出 → 处理下载弹窗 → 保存文件） | `download` 与 `dialog` 两个动作被 schema 拦死（CAP-05） | **AI 走不完最常见的企业流程** | **P0** |
| **SCN-05** | **AI 任务失败后人工接管续跑** | `HUMAN_ESCALATION` 无出边（CAP-06） | 89% 的任务升到人工后即死亡，用户被迫从头再来 | **P0** |
| **SCN-06** | **远程操作浏览器**（不开本机窗口，直接在 web 控制台里点击输入） | 查看器只能看截图（CAP-04） | 服务器部署场景下**基本不可用** | **P1** |
| **SCN-07** | **开发者接入自动化**（用 Playwright 驱动本产品的环境） | 只有任意 JS 执行接口，无标准协议（CAP-10） | 技术型客户无法集成 | **P1** |
| **SCN-08** | **非技术人员自助编排自动化**（拖拽式养号/发布） | 无 RPA 编辑器（CAP-09） | 自动化能力只对工程师可用 | **P1** |
| **SCN-09** | **AI 在真实业务网站上的通用性** | 100-task 基准中 **69.2% 的失败源于任务目标与测试站点内容不匹配**（非 Agent 能力问题） | 真实场景收益无法被证明；需要一套真实站点基准 | **P1** |
| **SCN-10** | **误操作找回**（删错环境、改错指纹） | 无备份/恢复、无操作审计、无回收站 | 数据不可逆丢失 | **P1** |

## 四、安全与合规缺口（SEC）

> 定义：可能造成数据泄露、资产损失或法律问题的缺口。**本组优先级最高，因为本系统集中托管账号密码、信用卡号与代理凭据。**

| ID | 缺口 | 证据 | 风险等级 | 修复成本 | 优先级 |
|---|---|---|---|---|---|
| **SEC-01** | **HTTP 服务零鉴权 + CORS 全开 + 绑定 0.0.0.0** | `app.use(cors())` 无白名单（`index.js:50`）；`app.listen(PORT)` 未传 host（`index.js:509`）；`server/` 无鉴权中间件 | 🔴 **致命**：同一局域网内任何来源可读写全部 API，包括 `GET /vault/:id`（脱敏）与 `POST /browser/:id/evaluate`（**执行任意 JS**） | 中（1 周） | **P0** |
| **SEC-02** | **主密钥缺失时静默降级为一次性内存随机密钥** | `vault.js:17-20`：缺失仅打 warn，用随机密钥 | 🔴 **致命**：用户未设 `FPB_MASTER_KEY` 时，凭据正常存入但**重启后永久不可解密**，且无任何强提示。这是「静默数据丢失」 | 小（改成启动时 fail-fast） | **P0** |
| **SEC-03** | **`/browser/:id/evaluate` 允许任意 JS 执行** | `index.js:297-310` | 🔴 高：配合 SEC-01 = 远程代码执行 | 中（加鉴权 + 白名单模式） | **P0** |
| **SEC-04** | **无操作审计日志** | — | 🟠 中高：出问题无法追责；企业客户合规必问（紫鸟/AdsPower 均有操作审计） | 中（与 CAP-01 同批） | **P1** |
| **SEC-05** | **无 LICENSE** | — | 🟠 中：**法律上不可分发/不可商用** | 极小 | **P0** |
| **SEC-06** | **凭据使用前无「隐形托管」访问控制** | `vault.js` 有加密存储，但任何能访问 API 的人都能读到明文（经解密） | 🟠 中：员工可带走账号明文。紫鸟的「密码隐形托管」（员工登录但看不到密码）是明确卖点 | 中（与 CAP-01 同批） | **P1** |
| **SEC-07** | **存储非原子写** | `db.js:52-55` | 🟠 中：写入中断 → JSON 文件损坏 → 全部 Profile 丢失 | 小（tmp+rename，`vault.js` 已有正确实现可复用） | **P1** |
| **SEC-08** | **无备份/恢复机制** | — | 🟠 中：无灾备能力 | 中 | **P1** |
| **SEC-09** | `multer` 声明为依赖但全仓库零调用 | `package.json` | 🟡 低：未使用依赖，扩大攻击面且误导 | 极小（删除） | **P2** |
| **SEC-10** | 无 GDPR / 数据合规说明 | — | 🟡 低（若只做国内）/ 中（若出海） | 小 | **P2** |

## 六、三条可选产品路线

当前产品处于岔路口。三条路线的取舍完全不同，**不可能同时走**：

### 路线 A —— 单机专业工具（对标 VMLogin / 云登）

- **做什么**：补齐 CAP-07（指纹六项）、CAP-03（导入导出）、CAP-02（批量）、ENG 全组；不做用户体系。
- **卖给谁**：个人卖家、小工作室、技术型用户（自托管、重视数据不出本机）。
- **工作量**：约 6–8 周。
- **优点**：最快能交付、能收钱；与本产品「自托管」的既有形态一致。
- **缺点**：天花板低，无法按席位收费，客单价受限。

### 路线 B —— 团队协作平台（对标 AdsPower / 比特浏览器）

- **做什么**：在 A 的基础上补齐 CAP-01（用户体系/权限/审计）、CAP-09（可视化 RPA）、CAP-12（群控）、SEC-06（密码隐形托管）。
- **卖给谁**：跨境运营团队、社媒矩阵工作室、电商代运营公司。
- **工作量**：约 4–6 个月，**需要一个团队而非一个人**。
- **优点**：商业价值最大，可按需/按席位收费，客户生命周期长。
- **缺点**：工作量最大；本产品目前的工程基础（无 git / 无 CI / 无测试）**支撑不了这个体量的协作开发**，必须先完成 P0。

### 路线 C —— AI Operator 作为差异化资产（对标紫鸟 Agent 方向）

- **做什么**：把 `server/agent/` 的「执行 / 验证 / 归因 / 恢复 / 修复」分层架构做成真正可用的能力：先解决 CAP-05（动作接线）、CAP-06（续跑）、SCN-09（真实站点基准），把业务成功率从 6% 拉到可信水平。
- **卖给谁**：目前无人可卖（6% 成功率），但这是**唯一真正差异化的资产**——竞品（AdsPower / 比特 / Multilogin / Kameleo）**没有一个具备这个架构深度**。
- **工作量**：完成接线 1–2 周；把成功率做到可交付水平 3–6 个月，且**必须先有一套真实站点基准**（当前基准 69.2% 的失败源于测试站点内容不匹配，不是 Agent 能力问题）。
- **优点**：长期护城河最深。
- **缺点**：短期零收入；且**没有 A 作为载体，AI 能力无处安放**。

### 我的判断

> **先走 A，用 A 的收入养 B，同时把 C 作为 A 的差异化卖点嵌入，而不是独立路线。**
>
> 理由：（1）C 的载体必须是 A —— 没有可用的环境管理能力，AI 再强也没有落点；（2）B 的工程量必须先有 P0 的工程基础才可能启动；（3）竞品已经证明了 A + RPA 能收钱，而 C 目前无人证明能收钱。

## 七、明确不该做的事

| 不该做 | 原因 |
|---|---|
| **继续为 benchmark 分数加 patch** | 100-task 基准中 69.2% 的失败源于测试站点内容与任务目标不匹配，不是 Agent 能力问题。继续 patch 只会把代码越改越复杂，收益趋近于 0 |
| **降低验证阈值 / 改 success definition 来提升成功率** | 那是自欺欺人。`DOM_CHANGED ≠ SUCCESS` 的严格语义是这个项目最值得保留的资产之一 |
| **在没有 git 和 CI 的情况下继续加功能** | 每加一个功能，技术债的利息都在复利增长。P0 的 8 项工程缺口总共约 2 周，必须先做 |
| **同时启动路线 A / B / C** | 三条路线的资源模型完全不同，同时走必然三条都走不通 |
| **重写 Agent 架构** | 架构本身质量高（分层清晰、可独立验证），缺的是接线与基准资产，不是重构 |
